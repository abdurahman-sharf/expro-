# وضع التجربة: الآثار الجانبية ومصفوفة الاختبار وسجل السجلات التجريبية

**شرط مسبق:** `progress.md` يسجّل وضع التجربة (المستخدم أكد أن النظام/الشركة تجريبية وأذن بإنشاء سجلات). بدونه لا
يُنفَّذ شيء من هذا الملف إلا بناء المصفوفة بخلايا `blocked`.

## المحتويات
1. قواعد الإنشاء · 2. التقاط الحالة قبل/بعد (Side-effect Diff) · 3. مصفوفة المتغيرات · 4. القيد المتوقع مقابل الفعلي ·
5. سجل السجلات التجريبية · 6. مثال كامل

## 1. قواعد الإنشاء (من `guardrails.md` §2.2)
- **عبر النماذج فقط:** افتح النموذج من الواجهة ← عبّئه ← اضغط زر الحفظ في الواجهة. لا تطلب رابط إجراء أبداً.
- **عملية واحدة في كل مرة**، وبعد كل عملية: التقاط "بعد" + تسجيل في الدفتر — قبل العملية التالية.
- **البادئة:** `اختبار-Claude-` في اسم كل سجل (`اختبار-Claude-عميل 1`، `اختبار-Claude-مورد 1`، `اختبار-Claude-منتج 1`)،
  وفي حقل المرجع/الملاحظات للمستندات (`اختبار-Claude-SM-004`). استخدم أرقاماً دائرية واضحة (10 × 100.00).
- **سجلات سابقة بالبادئة نفسها:** ابحث عنها قبل أول إنشاء. لا تعدّلها ولا تستخدمها في مستنداتك (لا تختر عميلاً أو منتجاً
  سابقاً، ولا تسجّل دفعة على فاتورة سابقة)، وابدأ تسلسلك بعد أعلى رقم موجود (`اختبار-Claude-عميل 2`)، ووثّقها في قسم
  "موجودة مسبقاً" في الدفتر.
- **الإجراءات اللاحقة** (دفعة على فاتورة، مرتجع، إشعار دائن) بنموذجها الخاص. **الإجراء بلا نموذج** (تأكيد التسليم،
  إلغاء التسليم، اعتماد بضغطة) يحتاج إذناً صريحاً لكل عملية.
- **ممنوع إلا بإذن خاص لكل عملية:** إقفال فترة/سنة، تعديل الإعدادات العامة أو الضرائب أو دليل الحسابات الأساسي، الحذف
  الجماعي، تفعيل/تعطيل الوحدات، أي إرسال خارجي (بريد/SMS/منصة الفوترة الإلكترونية) — احذر زر "حفظ وإرسال".
- **النماذج المضمّنة** (عميل جديد داخل الفاتورة): احفظ النموذج الفرعي بزره ثم الأساسي؛ كلاهما سجلان في الدفتر.

## 2. التقاط الحالة قبل وبعد (Side-effect Diff)

قبل كل إنشاء التقط لقطة **هيكلية** (عدد، آخر رقم، معرّفات) — لا تنسخ بيانات غير تجريبية إلى المخرجات:

| ما يُلتقط | كيف (الأسرع أولاً) | ما تبحث عنه بعد العملية |
|---|---|---|
| دليل الحسابات | API الحسابات (كل الصفحات) أو صفحة الدليل | حسابات جديدة (فرعي لكل عميل/مورد؟ حساب ضريبة يُنشأ عند أول استخدام؟) |
| القيود اليومية | API/قائمة القيود: آخر رقم قيد | القيود الجديدة: رقمها، مصدرها، كل سطر (الحساب/الدور، مدين، دائن، العملة) |
| أرصدة المخزون | بطاقة المنتج / API المخزون للمنتجات المعنية | الكمية والتكلفة قبل/بعد، طبقة FIFO جديدة؟ متوسط جديد؟ |
| سجل النشاط | صفحة سجل النشاط/التدقيق | ما سُجّل ومن ومتى |
| المستندات المرتبطة | صفحة المستند المرتبط | تغيّر الحالة (مثلاً "مدفوعة جزئياً")، الرصيد المتبقي |
| رصيد الطرف | بطاقة العميل/المورد أو كشف حسابه | الرصيد قبل/بعد |

اقرأ القيد من صفحة المستند (تبويب "القيد") أو من دفتر اليومية؛ إن كان داخل iframe فاقرأ `contentDocument` أو `src`.

وثّق الفرق في ملف الشاشة تحت **"الآثار الجانبية"**:
```markdown
## الآثار الجانبية (وضع التجربة — TR-002)
| الأثر | قبل | بعد | ملاحظة |
|---|---|---|---|
| حسابات جديدة | — | حساب فرعي تحت دور `clients` باسم العميل | يُنشأ تلقائياً عند حفظ العميل |
| قيود جديدة | آخر قيد JE-n | لا قيد | إنشاء العميل لا يولّد قيداً |
| سجل النشاط | — | "إضافة عميل" | |
```

## 3. مصفوفة المتغيرات

| المتغير | الحالات | لماذا يهم |
|---|---|---|
| نوع البند | منتج مخزني / خدمة / بند نصي حر | المخزني يولّد قيد تكلفة؛ النصي الحر يُوجَّه لحساب افتراضي قد يكون غير متوقع |
| الدفع | بدون / جزئي / كامل / دفعة مقدمة | حساب الخزينة، حالة المستند، تخصيص الدفعات |
| الحالة | مسودة / مُصدَر | هل تولّد المسودة قيداً أو تؤثر على الأرصدة؟ |
| العملة | أساسية / أجنبية | أعمدة العملتين، سعر الصرف، فروق العملة عند الدفع |
| الضريبة | بدون / غير شاملة / شاملة | حساب الضريبة، التقريب، إنشاء حسابات الضريبة تلقائياً |
| الخصم | على السطر / على الإجمالي / تسوية | هل للخصم حساب مستقل أم يُطرح من الإيراد؟ |
| الرصيد الافتتاحي | منتج برصيد افتتاحي / بدون | الحساب المقابل للرصيد الافتتاحي (أرصدة افتتاحية؟ حقوق ملكية؟ غيره؟) |

### المستندات الرئيسية (كلها في القالب — ما لا يوجد في النظام يُسجَّل `blocked` بسببه)

| المستند (`document`) | الخلايا |
|---|---|
| `sales_invoice` / `purchase_invoice` | المتغيرات السبعة أعلاه |
| `receipt` / `payment` | على فاتورة، دفعة مقدمة، بعملة أجنبية |
| `sales_return` / `purchase_return` / `credit_note` / `debit_note` | كلي، جزئي، لفاتورة مدفوعة، لصنف مخزني (هل يُعكس قيد التكلفة؟) |
| `fixed_asset` | شراء، إهلاك آلي، إهلاك يدوي (ثم قراءة الجدول الدوري)، بيع، تكهين، إعادة تقييم |
| `stock_count` | عجز، زيادة |
| `treasury_transfer` | بين خزينتين، خزينة ← بنك |
| `opening_balance` | عميل، مورد، منتج |
| `manual_journal` | متوازن، بسطر ضريبة (هل يتولّد سطر آلي؟) |

**خلايا سلوكية بلا قيد** (`expected_entry: []`، والنتيجة في `diff` إن خالفت المتوقع): حد ائتماني متجاوز · خزينة بالسالب
(صرف يتجاوز الرصيد) · مستند بتاريخ في فترة مقفلة · مسودة (لا رقم؟ لا قيد؟ لا أثر على الأرصدة؟) · منتج جديد برصيد
افتتاحي ثم فاتورة فورية (ذرّية قيد التكلفة).

في تشغيل ميداني لم تكن المرتجعات في المصفوفة أصلاً فبقيت قيودها [مُستنتج] في الحزمة النهائية — `coverage --write`
يسرد الآن "مستند بلا خلايا" لكل مستند رئيسي غائب عن المصفوفة.

**قبل أول خلية في كل وحدة:** اقرأ إعدادات الوحدة (افتراضيات الدفع والاستلام، الحساب المقابل لحركات المخزون، السعر الشامل
للضريبة، الأرصدة الافتتاحية والحد الائتماني) وسجّلها في رأس ملف الشاشة — افتراضي خطِر يغيّر القيد بصمت.

**الاستراتيجية:** خلية أساس + تغيير متغير واحد في كل مرة، ثم تراكيب يُشك في تفاعلها. رتّب حسب الأثر المحاسبي:
المخزني مقابل الخدمة مقابل النصي الحر، ثم الضريبة، ثم الدفع، ثم العملة، ثم الخصم، ثم الافتتاحي.

## 4. القيد المتوقع مقابل الفعلي

**قبل** الإنشاء اكتب القيد المتوقع محاسبياً بالأدوار (من المبادئ المحاسبية + توجيه الحسابات المعلن). **بعد** الإنشاء
اكتب الفعلي كما ظهر. صيغة الخلية في `04a-scenario-matrix.json`:
```json
{
  "id": "SM-007",
  "document": "purchase_invoice",
  "variables": {"item_type": "free_text", "tax": "exclusive", "payment": "none", "status": "issued", "currency": "base"},
  "status": "tested",
  "test_record": "TR-006",
  "expected_entry": [
    {"role": "purchases", "side": "debit", "amount": "net"},
    {"role": "vat_input", "side": "debit", "amount": "tax"},
    {"role": "suppliers", "side": "credit", "amount": "total"}
  ],
  "actual_entry": [
    {"role": "sales_cost", "side": "debit", "amount": "net"},
    {"role": "vat_input", "side": "debit", "amount": "tax"},
    {"role": "suppliers", "side": "credit", "amount": "total"}
  ],
  "diff": "البند النصي الحر رُحّل إلى sales_cost بدل purchases المعلن في توجيه الحسابات",
  "anomaly_ref": "AN-02"
}
```
- `amount_value` (اختياري، رقمي): المبلغ الفعلي بالأرقام الدائرية للسجل التجريبي، ليحسب `acs_tool.py expected-tb` الأرصدة.
- `test_record`: `TR-003` أو نطاق `TR-003..TR-005` — `acs_tool.py matrix` يتحقق أن كل واحد في الدفتر، وأن لكل `anomaly_ref`
  عنوان `### AN-xx` في `04-business-rules.md`.
- `amount` معادلة بالمتغيرات (`net`، `tax`، `total`، `qty*unit_cost`، `paid`، `total-paid`) لا أرقام حقيقية.
- `role`: دور الحساب لا رقمه. إن لم يكن للحساب دور معروف اكتب `account:<الاسم الوظيفي>` وسجّل سؤالاً.
- **كل `diff`** ⇒ بند في قسم التناقضات بـ `04-business-rules.md`:
```markdown
### AN-02: البند النصي الحر في فاتورة الشراء يُرحَّل إلى تكلفة المبيعات
- **المرصود (SM-007 / TR-006):** مدين `sales_cost` بصافي البند، بينما توجيه الحسابات يعلن `purchases`.
- **لماذا قد يكون خطأ:** يضخّم تكلفة المبيعات بمشتريات لم تُبع؛ يخالف التوجيه المعلن.
- **السلوك الصحيح المقترح:** يتبع التوجيه المعلن (`purchases`) ويكون قابلاً للإعداد لكل نوع بند.
- **سؤال مفتوح:** Q-xx — مقصود (سياسة "كل مشتريات غير مخزنية = تكلفة") أم خلل؟
- **اختبار للمنفّذ:** فاتورة شراء ببند نصي حر 100.00 + 15% ⇒ مدين purchases 100.00، مدين vat_input 15.00، دائن suppliers 115.00.
```
- الخلايا غير المختبرة: `"status": "untested"` أو `"blocked"` مع `"reason"` — تظهر في تقرير التغطية.
- بعد كل تحديث: `python3 <skill-dir>/scripts/acs_tool.py matrix --project <spec-dir>` ثم `progress`.

## 5. سجل السجلات التجريبية — `11-test-records-ledger.md`

قسمان: "سجلات أنشأتها هذه الدراسة" (TR-xxx)، و"موجودة مسبقاً" (سجلات بالبادئة وُجدت قبل البدء — لم تُعدَّل ولم تُستخدم).

يُحدَّث **فور** كل إنشاء (قبل العملية التالية):
```markdown
| # | النوع | الاسم | الرقم | الرابط | القيود الناتجة | الآثار الجانبية | الوقت |
|---|---|---|---|---|---|---|---|
| TR-001 | عميل | اختبار-Claude-عميل 1 | C-00xx | /clients/view/{id} | — | حساب فرعي تحت clients | 10:02 |
| TR-002 | منتج | اختبار-Claude-منتج 1 (رصيد افتتاحي 10) | P-00xx | /products/view/{id} | JE-n: مدين stores / دائن "أطراف دائنة أخرى" | AN-03 | 10:05 |
| TR-003 | فاتورة بيع | اختبار-Claude-SM-001 | INV-xxxx | /invoices/view/{id} | JE-n+1 إيراد، JE-n+2 تكلفة | حالة: غير مدفوعة | 10:09 |
```
- الأرقام والروابط هنا لسجلات **أنشأتها أنت** في بيئة تجريبية — مسموح ذكرها ليستطيع المستخدم إيجادها وحذفها.
- spec-writer يضيف في النهاية **ترتيب الحذف المقترح** (العكس): الدفعات ← المرتجعات/الإشعارات ← الفواتير ← حركات
  المخزون والقيود اليدوية ← الأطراف (عملاء/موردون) ← المنتجات، مع التنبيه أن الحذف يقوم به المستخدم (أو بإذن صريح
  لكل عملية)، وأن بعض الأنظمة تمنع حذف ما له قيود فيلزم الإلغاء/الإشعار الدائن أولاً.

## 6. مثال كامل مختصر (عميل + فاتورة)
1. التقاط "قبل": عدد الحسابات تحت `clients`، آخر قيد، رصيد المنتج.
2. إنشاء `اختبار-Claude-عميل 1` عبر نموذج العميل ← "بعد": حساب فرعي جديد تحت `clients`، لا قيد ← TR-001.
3. خلية SM-001 (فاتورة بيع، منتج مخزني، مُصدَرة، غير شاملة، بلا دفع): المتوقع مدين clients(total) / دائن sales(net) /
   دائن vat_output(tax) + مدين sales_cost(qty*cost) / دائن stores(qty*cost).
4. إنشاء الفاتورة عبر نموذجها ← "بعد": قيدان جديدان، المخزون نقص بالكمية ← قارن ← لا فرق ← TR-002 + خلية `tested`.
5. خلية SM-002 (نفسها + دفع جزئي عبر نموذج الدفعة) ← الفاتورة "مدفوعة جزئياً" ← TR-003.
6. `acs_tool.py matrix` و`progress`، وتحديث ملفات الشاشات بقسم "الآثار الجانبية".
