# دليل الجاهزية والنشر على قاعدة المالك

> الحالة (2026-10-30): **WP2.** يصف هذا الدليل الترتيب الذي تُنقل به **قاعدة بيانات حقيقية** إلى الإصدار الجديد، وما يقوله أمر الجاهزية `accounting:readiness` في كل خطوة. **الأمر يقرأ فقط**: لا يكتب ولا يوسم ولا ينقل ولا يقرّر شيئًا، إلا إذا طُلب `--apply`، وعندها لا يفعل إلا أن يستدعي أمرَين قائمَين بعلم التطبيق الخاص بكل منهما. لا دمج في `master` ولا نشر ولا تغيير على بيانات إنتاجية بقرار هذه الحزمة (E47): كل خطوة كتابة هنا **يأمر بها المالك** ويشغّلها بنفسه.

الخطوات الثماني أدناه هي نفسها التي يطبعها الأمر في آخر تقريره (`ReadinessRunbook`)، وينصّ اختبار على أن كل أمر مذكور هنا مذكور هناك والعكس، فلا يختلف الدليل عن الأمر.

## 1. ما هو الأمر

```
php spark accounting:readiness [--json] [--limit N] [--apply]
```

| الخيار | ما يفعله |
|---|---|
| (بلا خيار) | يشغّل **واحدًا وعشرين فحصًا** (عشرون وفحص الترحيل الرجعي `A6-BACKFILL`) داخل **معاملة قراءة فقط** واحدة (`SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`): قاعدة البيانات نفسها ترفض أي كتابة، وكل الفحوص ترى لقطة واحدة من الدفاتر مهما كان مستوى العزل الافتراضي للخادم (قيد حفظه موظف آخر أثناء التقرير لا يظهر لفحص متأخر ولا يخفى على فحص مبكر). يطبع تقريرًا مقروءًا وينتهي بالـ`RUNBOOK` |
| `--json` | يطبع مستندًا واحدًا صالحًا من JSON ولا شيء غيره (الحالة والأعداد وكل فحص بنتائجه كاملة وخطوات الدليل) لتحفظه قبل الترحيل وبعده وتقارن؛ **اطلب معه `--no-header` الخاص بـ`spark`** وإلا سبق المستند شعارُ `spark` فلا يكون الملف JSON صالحًا |
| `--limit N` | عدد النتائج المطبوعة لكل فحص (الافتراضي 20، و`0` للكل)؛ عدد صحيح موجب أو صفر، وغير ذلك يُرفض برمز `7`. الـJSON فيه الكل (فحوص الدفتر تحتفظ بأول 1000 نتيجة وتقول ذلك في `data.truncated`) |
| `--apply` | يطبع التقرير (`before --apply`) ثم يشغّل الأوامر القائمة التي تعالج ما **فشل**، كلًّا بعلمها: `accounting:stamp_payments --apply` و`accounting:bank_accounts --move`، ثم يعيد التقرير (`after --apply`)؛ فيبقى أثر ما كان وما صار، ويبقى التقرير الأول إن انكسر أحد الأمرَين. إن لم يفشل ما يعالجه أمر قائم لم يشغّل شيئًا وطبع التقرير مرة واحدة. **لا يكتب شيئًا غير ذلك.** لا يُجمع مع `--json` |

**رمز الخروج:** `0` فقط حين لا يفشل فحص ولا ينكسر؛ `1` فيما عدا ذلك؛ و`7` (`EXIT_USER_INPUT`) لخيار يرفضه الأمر قبل أن يقرأ شيئًا: `--limit` بلا رقم صحيح أو بلا قيمة أو بقيمة سالبة، و`--apply` مع `--json`.

**الحالات:** `PASS` يمرّ. `FAIL` يوقف الجاهزية ويُعالَج أو يقبله المالك كتابةً. `ERROR` فحص لم يستطع العمل (يوقف الجاهزية كالفشل). `REVIEW` للمالك أن ينظر فيه ولا يوقف (من يملك صلاحية حساسة، والتفعيل، والترحيلات المنتظرة، والمخزون الافتتاحي). `SKIPPED` لم يُفحص لأن الجدول أو العمود لم يوجد بعد (ترحيل منتظر): يظهر **قبل** الترحيلات ويختفي **بعدها**.

**المرحلة:** يقول التقرير `pre-migration` ما دام في القاعدة ترحيل منتظر، و`post-migration` حين لا يبقى. **يُجرى قبل الترحيلات ثم بعدها**، والمطلوب بعدها `post-migration` برمز `0`.

## 2. الفحوص وما يقرؤه كل منها

كل فحص يعيد استعمال مكتبة الأمر القائم الذي يملكه (لا SQL مكرَّر في مواضع الفحص نفسه)، وعمود «الحالة عند المشكلة» يقول أيها يعالجه `--apply`.

| المرجع | ما يُفحص | من أين يُقرأ | الحالة عند المشكلة |
|---|---|---|---|
| `MIGRATIONS` | الترحيلات المنتظرة بترتيبها مع وسم **DATA** (تعيد كتابة صفوف أو تفتح حسابات) و**HEAVY** (تعدّل جدولًا كبيرًا) | `MigrationChecks` وجدول `migrations` كما هو (لا يُنشأ إن غاب) | REVIEW |
| `E38-SCAN` | أسطر الشراء القديمة بخصم **ثابت** وكمية غير واحدة التي لا تحسمها الدفاتر ولا التاريخ ولا قرار مسجَّل | `LegacyPurchaseDiscount::plan()` و`marked()` (الأمر `accounting:purchase_discount`) | FAIL (غير محسومة) / REVIEW (محسومة بقرار مسجَّل ينتظر تأكيد المالك). **صفر صفوف تتغير**، والترحيل نفسه يتوقف بلا تغيير عند أي سطر غير محسوم. يطبع لكل سطر غير محسوم **فرق المبلغين** بين قراءتَي الخصم (للوحدة وللسطر كله) ومجموعه في `data.at_stake`؛ وقبل الترحيل `data.would_mark` و`data.would_mark_discount` (ما سيعلّمه الترحيل وخصمه)، وبعده `data.marked_lines` و`data.marked_discount` ليُقارَنا |
| `E40-BANK-DETAILS` (مكان الحساب) | حسابات الخزائن البنكية التي ليست تحت الحساب الرئيسي للبنوك `1202` | `BankAccountPlacement::pending()` | FAIL، يعالجه `accounting:bank_accounts --move` |
| `E40-BANK-DETAILS` (البيانات) | خزائن بنكية بلا اسم بنك أو بلا رقم حساب | `BankAccountPlacement::incomplete()` | FAIL، يُكمَل من شاشة الخزائن (E40: لا يُعدَّل شيء تلقائيًا) |
| `E41-STAMP` | دفعات بيع وشراء لا تسمّي خزينة مع أن قيدها دخل خزينة، حيث حساب الخزينة يساوي حساب قيد الدفعة | `PaymentTreasuryStamping::plan()` | FAIL، يعالجه `accounting:stamp_payments --apply` (يوسم الخزينة وحدها: لا قيد ولا مبلغ ولا رصيد) |
| `LEDGER-BALANCE` | قيود مرحَّلة لا تتوازن، أو مجاميع رأسها تخالف سطورها | `accounting_journals` و`accounting_journal_lines` | FAIL |
| `LEDGER-LINES` | قيود مرحَّلة بلا سطور | `accounting_journals` | FAIL |
| `LEDGER-PERIODS` | قيد رُحِّل داخل فترة كانت مقفلة وقتها، أو يقع خارج كل سنة مالية | `accounting_closed_periods` (مرتبة بالفرع) و`accounting_fiscal_years` | FAIL |
| `LEDGER-SOURCE-KEYS` | مستند له أكثر من قيد مرحَّل بمفتاح المصدر نفسه، أو قيد عُكس أكثر من مرة | `accounting_journals` | FAIL |
| `WP8-NUMBERING` | عدّاد تسلسل مفعَّل سيعطي رقمًا سبق إعطاؤه، وسلسلة القيود اليدوية أقل من أعلى رقم | `DocumentNumbering` و`AccountingSettings::lastManualNumber()` | FAIL (للمعطَّل ملاحظة فقط) |
| `TIE-CUSTOMERS` | رصيد حساب كل عميل مقابل فواتيره ورصيده الدائن وأعماره | `CustomerLedger::position()` | FAIL |
| `TIE-SUPPLIERS` | رصيد حساب كل مورد مقابل مشترياته ورصيده الدائن وأعماره | `SupplierLedger::position()` | FAIL |
| `TIE-TREASURIES` | رصيد كل خزينة مقابل حسابها (ما أُضيف بالقيد اليدوي يظهر) | `TreasuryService::position()` | FAIL |
| `TIE-STOCK` | كل موقع مخزون: رصيد حسابه مقابل حركاته المقيَّمة، وكل قيد مقابل حركاته | `StockLedger::reconcile()` و`mismatchedJournals()` | FAIL |
| `WP7-PRE-DEPLOY-QUERY` | قيود على الحسابين بين الفروع (`12044` و`2214`) لا تأتي من تحويل ولا تسوية ولا دفعة عبر الفروع | `accounting_journals` و`accounting_interbranch_legs` | REVIEW (تظهر «غير منسوبة» ولا تُعدَّل) |
| `TIE-BRANCHES` | الحسابان بين الفروع يتقابلان على مستوى الشركة (`InterBranchPosition::difference()`)، وكل زوج فروع متفق (`InterBranchBalances`) | `InterBranchPosition` و`InterBranchBalances` | FAIL |
| `OWNER-GRANTS` | **من يملك كل صلاحية حساسة** (`AccountingGuard::SENSITIVE`) وبأي فروع، ليراجعها المالك | `SensitivePermissions::holders()` | REVIEW إن وُجد حامل |
| `E26-ACTIVATION` (التفعيل) | هل المحاسبة مفعَّلة، وما ينقصها قبل التفعيل | `AccountingSettings::readiness()` و`notices()` | REVIEW مطفأة (تبقى مطفأة حتى يأمر المالك)، FAIL إن كانت مفعَّلة وإعداداتها ناقصة |
| `E26-ACTIVATION` (المخزون الافتتاحي) | مواقع بمخزون افتتاحي منتظر الترحيل أو مرحَّل جزئيًا أو محجوب | `OpeningStock::plans()` | REVIEW (الترحيل بأمر المالك، E26) |
| `E26-ACTIVATION` (الأرصدة الافتتاحية) | لكل فرع: مرحَّلة أو مسودة محفوظة أو لم تُدخَل | `OpeningBalanceService::state()` | REVIEW للمسودة غير المرحَّلة |
| `A6-BACKFILL` | **الترحيل بأثر رجعي (WP12):** ما يشترطه اعتماد دفعة (الإعداد `accounting_backfill_enabled` وتاريخ البدء والرصيد الافتتاحي المرحَّل لكل فرع) وما ينقص منها، والدفعات المفتوحة بأعدادها، **ومعاينات لا تخص دفعة مفتوحة** (يجب ألا توجد)، وعدد المستندات بلا قيد لكل عائلة (مبيعات ومرتجعات ومشتريات ومصروفات وإقفالات صندوق) | `BackfillChecks` و`BackfillService::approvalBlockers()` وجداول الدفعات والمعاينات | FAIL إن وُجدت معاينة لا تخص دفعة مفتوحة (لا يحذفها الأمر)، REVIEW إن كان الترحيل الرجعي مفعَّلًا أو وُجدت دفعة مفتوحة أو مستندات بلا قيد، PASS إن كان مطفأً ولا دفعة مفتوحة ولكل مستند قيده؛ SKIPPED قبل ترحيل `RetroactiveBackfill`. **الأمر يقرأ فقط ولا يشغّل الترحيل الرجعي**، والدفعة تُنشأ وتُعتمد من شاشة «مستندات سابقة» بإذنك |

**ما لا يفحصه الأمر:** لا يحكم على صواب الأرقام الافتتاحية ولا على أن أسماء البنوك صحيحة؛ يُظهر فقط ما ينقص أو لا يتفق. وفحص الحسابات `12044` و`2214` يقرأ ما هو في القاعدة: القيد اليدوي عليهما يظهر فرقًا حتى ينظر فيه أحد.

## 3. الترتيب (RUNBOOK)

> **قبل كل شيء:** لا يُشغَّل شيء من هذا على قاعدة المالك الحقيقية إلا بأمره. ابدأ بنسخة مستعادة من النسخة الاحتياطية في قاعدة تجريبية: هذه هي البروفة.

### الخطوة 1. النسخة الاحتياطية (E54)

لا يعمل ترحيل قبل أن توجد نسخة **ومعها استعادة مجرَّبة**.

```
mysqldump --single-transaction --routines --triggers -u USER -p DATABASE > backup-before-release.sql
```

- انسخ مجلد `writable/` (فيه `writable/accounting_attachments`) وملف `.env` بجوار الملف.
- استعد النسخة في قاعدة تجريبية (`mysql -u USER -p SCRATCH < backup-before-release.sql`) وشغّل الأمر عليها أولًا: هذه هي البروفة. لا تكتب اسم القاعدة الحية هناك.
- لا يحفظ أحدٌ بيعًا أو شراءً بين النسخة والترحيلات.

### الخطوة 2. الجاهزية قبل الترحيلات

```
php spark accounting:readiness
php spark accounting:readiness --json --no-header > readiness-before.json
```

- المطلوب رمز `0` للمتابعة. كل `FAIL` يُعالَج في الخطوة التالية أو يقبله المالك كتابةً.
- في هذه المرحلة يظهر `SKIPPED` لما لم تصله الترحيلات بعد، ويظهر `E38-SCAN` لأن ترحيل الخصم لم يعمل.
- التقرير يقرأ فقط: لا يوسم ولا ينقل ولا يقرّر.
- اطلب `--no-header` مع `--json`: بدونه يطبع `spark` شعاره قبل المستند فلا يكون الملف JSON صالحًا.

### الخطوة 3. قرّر ما فشل

```
php spark accounting:purchase_discount
php spark accounting:purchase_discount resolve --before "YYYY-MM-DD HH:MM:SS"
php spark accounting:stamp_payments
php spark accounting:bank_accounts
```

- **E38:** قرّر أسطر الشراء التي لا دليل عليها (`resolve` يأخذ `--before` أو `--all-legacy` أو `--none-legacy`)، واللحظة هي أول مرة شغّلت فيها هذه القاعدة الخصم للوحدة. الترحيل `LegacyFixedPurchaseDiscount` يتوقف بلا تغيير ما دام سطر غير محسوم. القرار يُسجَّل في الإعدادات ولا يغيّر سطرًا.
- **E41:** الوسم يضع خزينة الدفعة وحدها، حيث يطابق حساب الخزينة حساب قيد الدفعة. بأمر المالك: `php spark accounting:stamp_payments --apply` أو `php spark accounting:readiness --apply`.
- **E40:** تنتقل حسابات البنوك تحت `1202` بالترحيل `BankAccounts` أو بـ`php spark accounting:bank_accounts --move` (يتغير الأب والرمز وحدهما، ببصمة لسطور القيود قبل وبعد)، ويُكمَل اسم البنك ورقم الحساب من شاشة الخزائن.

### الخطوة 4. شغّل الترحيلات بهذا الترتيب

```
php spark migrate -n App
```

- ترتيب التشغيل هو ترتيب أرقام الإصدارات، وكل خطوة تعتمد على ما قبلها. يطبع الأمر الترحيلات المنتظرة **فعلًا** في قاعدتك بوسمها.
- **DATA** تعيد كتابة صفوف قائمة أو تصنّفها أو تضيف إلى الدليل: `BranchesFoundation` و`AccountingRouting` و`PurchasesAccounting` و`LegacyFixedPurchaseDiscount` و`BankAccounts` و`InterBranchTransfers`، و`ChequesAndRevenues` (يفتح أربعة حسابات فرعية للشيكات في دليل قائم ويوجّه أربعة مفاتيح إليها، **ولا يفتح حسابًا إن غاب أبوه** `1206` أو `212` أو `54` فيُراجَع التوجيه بعده)، و`InvoiceHeaderCharges` (الموجة 5: يفتح حسابي «تسويات المبيعات» `4204` و«إيرادات الشحن» `4208` بأول رمز حرّ من أربعة في دليل قائم ويوجّه صفّي `sales.adjustment` و`sales.shipping` إليهما، **وينقل صف التسوية القديم عن الخصم المسموح به فقط إن لم يغيّره أحد**: يُراجَع التوجيه بعده).
- **HEAVY** تعدّل جدولًا كبيرًا فتُشغَّل في ساعة هادئة: `SalesAccounting` و`SalesReceivables` و`CostPrecision` و`ReceivingCostPrecision` و`Treasuries` و`StockTransfersBetweenBranches` و`ExpensesAccounting` و`PurchaseInvoiceDiscount` و`SalesInvoiceDiscount` و`CrossBranchPayments` و`RefundInvoice` و`SupplierPaymentDate` و`InvoiceDatesAndPaymentTerms` و`PurchaseTaxesAndSupplierRegistry`، و`CustomerOpenings` (يعيد بناء `customer_credit_applications` ليقبل `invoice_sale_id` الفراغ) و`QuoteLifecycle` (عمودان وفهرس على `sales`) و`AppConfigValueText` (يوسّع عمود `app_config.value` إلى `TEXT` في جدول من نواة OSPOS، صغير، ولا رجوع تلقائيًا عنه: نسخة احتياطية قبله). وسُجِّل `ChequesAndRevenues` بوسم **DATA** (يفتح أربعة حسابات فرعية ويوجّه أربعة صفوف توجيه في دليل قائم). **وأضافت الموجة 5:** `PerTaxInclusive` (عمود وفهرس على `sales_items_taxes` وجدول `tax_definitions`) و`BankReconciliation` (عمود فارغ `treasuries.bank_code` وخمسة جداول جديدة) و`SalesDebitNotes` (جدول وعمود `customer_credit_applications.debit_note_id` واستبدال قاعدة «الهدف الواحد»: **يعيد بناء `customer_credit_applications` للمرة الثانية بعد `CustomerOpenings`**) و`PricingAndCreditControls` (أعمدة بقيم محايدة على `customers` و`sales` و`items` وجدولان): كلها بنسخة احتياطية قبلها وفي ساعة هادئة.
- **إضافية بلا وسم** (تنشئ جداول وتسجّل صلاحيات ولا تعدّل جدولًا قائمًا، فيطبعها الأمر «إضافية»): `YearEndClosings` (جدول وصلاحية) و`CreditFlows` (ستة جداول وأربع صلاحيات). الصلاحيات الجديدة كلها بلا منح، ويعدّد التقرير حاملي الحساسة منها في الخطوة 6. **ومن الموجة 5:** `RetroactiveBackfill` (يوسّع جدول `accounting_backfill_batches` الذي أنشأه الأساس ولم يستعمله كود وينشئ `accounting_backfill_items` ويكتب `accounting_backfill_enabled` = `0` ويسجّل الصلاحية الحساسة `acc_backfill_manage`؛ **مستثنى في `MigrationChecksTest`** لأنه يعدّل جدولًا أنشأه الإصدار نفسه) و`RolesAndRecordScope` و`RolesPermissions` (خمسة جداول جديدة ووحدة `roles` والصلاحية الحساسة `acc_roles_manage`، ولا يعدّلان جدولًا قائمًا). **وبعد الموجة 5 فُحصت ملفات الترحيل كلها (94 ملفًا) ببرنامج يطبّق قاعدة `MigrationChecksTest`: لا ترحيل يعدّل جدولًا وهو غير مصنَّف ولا مستثنى** (فلا بند كـ`AppConfigValueText` الذي سبق).
- أول دخول بعد النشر ينفّذ الترحيلات نفسها تلقائيًا: شغّلها هنا **عمدًا** قبل أن يدخل أحد.
- توقّف عند أول فشل واستعد النسخة؛ لا تعدّل جدول `migrations` بيدك.

### الخطوة 5. ما بعد الترحيل

```
php spark accounting:readiness
php spark accounting:readiness --json --no-header > readiness-after.json
php spark accounting:bank_accounts
php spark accounting:check_locks
php spark accounting:status
```

- يجب أن يقول التقرير `post-migration` وأن يخرج بـ`0`، وألا يبقى حساب بنك خارج `1202`.
- قارن `readiness-before.json` بـ`readiness-after.json` (`diff` أو `jq` على `.checks[].data`): `would_mark` و`would_mark_discount` في فحص `E38-SCAN` قبل يجب أن يساويا `marked_lines` و`marked_discount` بعد، فأسطر الشراء التي علّمها الترحيل هي التي سمّاها التقرير بخصمها نفسه.
- `TIE-SUPPLIERS` و`TIE-CUSTOMERS` يُتخطَّيان (`SKIPPED`) قبل الترحيلات ما دامت الدفاتر لم تُنشأ بعد، ويجب أن يقولا الآن `PASS`: هذا هو الدليل على أن حساب كل مورد وعميل يتفق مع مستنداته ورصيده الدائن وأعماره.
- افتح الأرصدة بين الفروع وشاشة الخزائن وانظر في ما عدّه التقرير للمراجعة.

### الخطوة 6. راجع من يملك الصلاحيات الحساسة (OWNER-GRANTS)

لا أمر هنا. يعدّد التقرير حاملي كل صلاحية حساسة وفروعهم؛ والمدير يمنح ويسحب بيده من نموذج الموظف. **لا ترحيل يمنح صلاحية حساسة لأحد.** القائمة تُقرأ من `AccountingGuard::SENSITIVE` وقت التشغيل، فتشمل كل صلاحية حساسة مسجَّلة في هذا الإصدار، وتُنبَّه الصلاحية التي لم تُسجَّل بعد بـ`[not registered yet]`.

### الخطوة 7. لا تفعّل المحاسبة إلا بأمر المالك (E26)

```
php spark accounting:fill_accounts
php spark accounting:enable --currency=SAR --start-date=YYYY-MM-DD --fiscal-year-end=YYYY-MM-DD
```

- تبقى المحاسبة **معطَّلة على أي نشاط حقيقي** حتى يأمر المالك بالتفعيل (D1: التعطيل يعني سلوك OSPOS كما هو).
- بعد التفعيل يُرحَّل المخزون الافتتاحي من شاشة الأرصدة الافتتاحية، موقعًا موقعًا (E26).
- يبقى خصم إجمالي فاتورة الشراء مطفأً في الإنتاج حتى إذن منفصل من المالك (E47 وE54).
- **الترحيل الرجعي (WP12):** المستندات التي حُفظت والمحاسبة مطفأة (أو قبل أن يتبعها الدفتر) لا قيد لها؛ يعدّها فحص `A6-BACKFILL` ويعدّها التشغيل الجاف للقراءة فقط `php spark accounting:backfill --from ... --to ...`، وتُنشأ الدفعة وتُعاين وتُعتمد من شاشة «مستندات سابقة» **ولا تُعتمد على قاعدة إنتاجية بلا إذنك المنفصل** (E47). الاعتماد مطفأ بالإعداد `accounting_backfill_enabled` وبالصلاحية الحساسة `acc_backfill_manage` (بلا منح لأحد)، ويشترط الرصيد الافتتاحي المرحَّل لكل فرع وتاريخ البدء، **وتُعتمد الدفعة قبل ترحيل المخزون الافتتاحي لمواقع المستندات التي تحرّك مخزونًا** (وإلا رُفض المستند `stock_opened_after`). **نسخة احتياطية قبل أي دفعة.**

### الخطوة 8. التراجع باستعادة النسخة

```
mysqldump --single-transaction -u USER -p DATABASE > state-after-failed-release.sql
mysql -u USER -p -e "DROP DATABASE DATABASE; CREATE DATABASE DATABASE CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci"
mysql -u USER -p DATABASE < backup-before-release.sql
```

- تُستعاد النسخة في قاعدة **فارغة**: ملف النسخة يُسقط ويعيد إنشاء الجداول التي فيه وحدها، فاستعادته فوق القاعدة الحية تترك الجداول التي أنشأها الإصدار (`accounting_journals` وغيرها) بصفوفها، وقيودها ستصادف مبيعات تعيد استعمال أرقامها.
- الأمر الأول يحفظ ما تركه الإصدار الفاشل للفحص بعد الحادثة؛ والثاني يحتاج حق إسقاط القاعدة وإنشائها، ويستعمل ترميز `app/Config/Database.php` وتجميعه.
- `down()` ليس تراجعًا للترحيلات التي تعيد كتابة البيانات: `LegacyFixedPurchaseDiscount` يغيّر معنى الخصم، و`BankAccounts` لا يعيد الحسابات إلى مكانها، و`PurchaseInvoiceDiscount` يرفض متى استعمله شراء.
- أعد الشيفرة إلى الإصدار السابق **مع** الاستعادة، وشغّل التقرير على القاعدة المستعادة.

## 4. ثوابت الأمر

- كل فحص قراءة فقط. `ReadinessRunner` يفتح معاملة `READ ONLY` بمستوى العزل `REPEATABLE READ` المسمّى صراحةً (لا يُترك لافتراضي الخادم) ويُنهيها بتراجع في كل حال؛ وإن لم يقبل الاتصال معاملة قراءة فقط قال التقرير ذلك صراحة وبقيت الفحوص داخل معاملة تُلغى في النهاية، فيُرجَع ما قد يكون كتبه فحص (ولقطتها حينئذ ما يعطيه الخادم).
- فحص لا يجد جدوله أو عموده لا يفشل ولا يوقف التقرير: يُوسم `SKIPPED`. وفحص ينكسر يُوسم `ERROR` ولا يخفي بقية الفحوص.
- `--apply` لا يستدعي إلا `accounting:stamp_payments --apply` و`accounting:bank_accounts --move`، وفي ترتيب الفحوص، ولا يستدعيهما إن لم يفشل فحصهما. لا يقرّر القرار E38 ولا يكمل اسم بنك ولا يعدّل قيدًا.
- لا يمسّ الأمر قيدًا ولا دفعة ولا رصيدًا. الوسم يضع خزينة الدفعة وحدها، ونقل حساب البنك يغيّر موضعه في الدليل وحده.
