# تحويل «الاول برو» إلى نظام محاسبي متكامل

تحليل الوضع الحالي، والفجوة مع نظام محاسبي كامل، وخطة مراحل مقترحة.

- **الحالة:** مرحلة التحليل فقط. لم يُكتب كود تطبيق، والخطة بانتظار موافقة المالك على القرارات في القسم 4.
- [ملاحظات من نظام دفترة](daftra-observations.md): الأدلة التي بُنيت عليها الفجوة.

## 1. أين نقف اليوم

| موجود في OSPOS | غير موجود |
|---|---|
| نقطة بيع وفواتير وعروض أسعار وأوامر عمل ومرتجعات (`Sale::save_value`) | دليل حسابات |
| استلام مشتريات بمورد ونوع دفع نصي (`Receiving`) | قيود يومية ودفتر أستاذ |
| أصناف ومخزون بسجل حركات (`inventory`) وسعر تكلفة محفوظ في كل بند بيع (`item_cost_price`) | سنوات مالية وفترات مغلقة |
| ضرائب بتفصيل لكل بيع (`sales_taxes`) وولايات ضريبية | ذمم عملاء وموردين (لا كشف حساب ولا مدفوعات موردين) |
| مصروفات بفئات (`expenses`)، وإقفال صندوق (`cash_up`) | حسابات بنكية وخزائن وشيكات |
| نحو 20 تقريرًا تشغيليًا، ولوحة بداية، وPDF بـmPDF، وChart.js | أصول ثابتة وإهلاك، ومراكز تكلفة |
| صلاحيات بالوحدات (`modules`/`permissions`/`grants`) وواجهة Bootstrap 5 بـRTL | ميزان مراجعة وقائمة دخل ومركز مالي وتدفق نقدي |

**الخلاصة:** البيانات اللازمة لاشتقاق القيود موجودة في معظمها (مبالغ، تكلفة، ضريبة، مدفوعات، مخزون)، لكنها موزعة بلا طبقة قيد مزدوج تجمعها. الفجوة الحقيقية هي **طبقة محاسبة** فوق الوحدات الحالية، وليست إعادة كتابتها.

## 2. ما يجب أن يتعلمه النظام من دفترة

1. المحاسبة قسم مستقل يُغذَّى بترحيل تلقائي من المبيعات والمشتريات والمصروفات، ويقبل قيودًا يدوية بترقيم مستقل.
2. ربط المستندات بالحسابات **قابل للضبط** (شاشة توجيه الحسابات) مع حساب افتراضي، وليس مثبتًا في الكود.
3. فترات مالية وإقفال يمنعان التعديل بأثر رجعي.
4. القيد له مسودة وحالة ومصدر وسجل تعديلات، ومركز تكلفة وضريبة على مستوى السطر.
5. تقارير مالية تُشتق من القيود: قائمة دخل، مركز مالي، تدفق نقدي، كشف حساب، أعمار ذمم.

التفاصيل والأدلة في [الملاحظات](daftra-observations.md).

## 3. التصميم المقترح

### نموذج البيانات (جداول جديدة بالبادئة `ospos_`)

| الجدول | الغرض |
|---|---|
| `accounting_accounts` | شجرة الحسابات: `parent_id`، `code` فريد، `type` (أصل/خصم/حقوق/إيراد/مصروف)، `is_group`، `system_key` لحسابات النظام (نقدية، مبيعات، تكلفة مبيعات، ضريبة مخرجات…) |
| `accounting_journals` | رأس القيد: رقم، تاريخ، `source_type`/`source_id`، حالة (مسودة/مرحّل/معكوس)، `reverses_journal_id`، من أنشأه |
| `accounting_journal_lines` | الأسطر: حساب، مدين، دائن (`decimal(15,4)`)، وصف، مركز تكلفة، `party_type`/`party_id` (عميل/مورد) |
| `accounting_fiscal_years` و`accounting_closed_periods` | السنوات المالية ونطاقات الإقفال |
| `accounting_routing` | مفتاح بند → حساب (مبيعات، مرتجعات، خصم، ضريبة، تكلفة مبيعات، مخزون، ذمم، لكل نوع دفع، لكل فئة مصروف) |
| `accounting_cost_centers` | شجرة مراكز التكلفة (لاحقًا) |

### محرك الترحيل

- خدمة واحدة معزولة في `App\Libraries\Accounting` (مثلًا `Posting_lib`)، تُستدعى من نقاط الحفظ الحالية **داخل نفس معاملة قاعدة البيانات**: `Sale::save_value` وإلغاء/استعادة المبيعات، `Receiving::save_value`، `Expense::save_value` و`delete_list`، `Cashup::save_value`.
- لا يُرحَّل إلا البيع المكتمل (`COMPLETED`) من نوع نقطة بيع أو فاتورة أو مرتجع. العروض وأوامر العمل والمبيعات المعلقة والملغاة لا تُرحَّل.
- مثال البيع: مدين نقدية/بنك/بطاقة (لكل دفعة) وذمم عملاء (المتبقي)؛ دائن مبيعات وضريبة مخرجات؛ ثم مدين تكلفة مبيعات ودائن مخزون من `item_cost_price × الكمية`. المرتجع يعكسها.
- التعديل أو الإلغاء يولّد **قيدًا عكسيًا** ثم قيدًا جديدًا، ولا يُعدَّل قيد مرحّل ولا يُحذف.
- مفتاح تشغيل `accounting_enabled` في `app_config`: النظام يعمل كما هو عند تعطيله.

### الواجهة والصلاحيات

- وحدة `accounting` بصلاحيات فرعية (دليل، قيود، فترات، توجيه، تقارير) في `modules`/`permissions`/`grants`، ومجموعة `group_accounting` في `navigation_helper.php`.
- شاشات القوائم والنماذج بنمط P5 الموحد، والتقارير داخل فهرس التقارير الحالي (P6).

## 4. القرارات المطلوبة منك

| # | القرار | التوصية | السبب |
|---|---|---|---|
| D1 | المحاسبة اختيارية أم إلزامية؟ | اختيارية بمفتاح تشغيل | لا تكسر المتاجر والبيانات الحالية |
| D2 | عند فشل الترحيل: نوقف البيع أم نسجّل خطأ؟ | نوقفه داخل المعاملة، ونمنع التفعيل أصلًا حتى تكتمل خريطة التوجيه | لا مبيعات بلا قيد، والفشل الفعلي لن يحدث إلا بخلل برمجي |
| D3 | الترحيل الرجعي للبيانات القديمة؟ | أداة اختيارية بتشغيل تجريبي (dry-run) وتاريخ بدء + قيد رصيد افتتاحي | لا يُفرض على ما قبل تاريخ البدء |
| D4 | العملات | عملة أساسية واحدة الآن | OSPOS نفسه لا يدعم تعدد العملات |
| D5 | الذمم | عبر `party_type/party_id` على أسطر القيد بدل حساب فرعي لكل عميل | أبسط، وتقارير الأعمار تُشتق منه |
| D6 | دليل الحسابات الافتراضي | دليل عربي قياسي بترميزنا نحن، قابل للتعديل | لا ننسخ ترميز دفترة |
| D7 | الضريبة والفاتورة الإلكترونية (ZATCA) | خارج النطاق الأول، مع ضريبة قيمة مضافة كحسابات في القيد | دفترة تدعم الربط، لكنه مشروع مستقل |
| D8 | الأصول الثابتة ومراكز التكلفة | في النسخة الأخيرة | أقل أولوية من الدورة الأساسية |

## 5. المراحل المقترحة

| المرحلة | المحتوى | بوابة القبول |
|---|---|---|
| **A0** الأساس | ترحيلات الجداول، نماذج `Account` و`Journal`، دليل حسابات افتراضي، مفتاح التشغيل | مجموع المدين = الدائن مفروض في الخدمة والاختبارات، وCI أخضر، وترحيلات إضافية فقط |
| **A1** الدليل والقيود اليدوية | شاشة شجرة الحسابات، قيد يدوي بمسودة وترحيل وعكس، ترقيم مستقل، سجل تعديلات | قيد يدوي متوازن يُرحَّل ويُعكس، وغير المتوازن يُرفض |
| **A2** الفترات والإقفال | سنوات مالية، فترات مغلقة، رصيد افتتاحي | لا قيد ولا بيع جديد داخل فترة مغلقة |
| **A3** توجيه الحسابات وترحيل المبيعات | شاشة التوجيه، ترحيل البيع والمرتجع والضريبة والخصم والتكلفة، إلغاء/استعادة، إقفال الصندوق | لكل سيناريو بيع قيد متوازن، ومجموع المبيعات في القيود يطابق تقرير المبيعات |
| **A4** المشتريات والمصروفات والمخزون | ترحيل الاستلام، **مدفوعات الموردين (جديد)**، المصروفات بفئة→حساب، تسويات المخزون | ذمم الموردين تطابق الاستلامات والمدفوعات |
| **A5** الخزائن والبنوك والشيكات | حسابات نقدية وبنكية، سندات قبض وصرف، شيكات | أرصدة الخزائن تطابق القيود |
| **A6** التقارير المالية | ميزان مراجعة، كشف حساب، قائمة دخل، مركز مالي، تدفق نقدي، أعمار ذمم، ضريبة القيمة المضافة، PDF وChart.js | الميزان متوازن، والمركز المالي: الأصول = الخصوم + حقوق الملكية |
| **A7** الأصول ومراكز التكلفة | أصول وإهلاك بقيود تلقائية، مراكز تكلفة بنسب توزيع | قيد إهلاك شهري صحيح، وتقرير مراكز التكلفة يطابق القيود |

مقترح البداية: **A0 + A1**. تعطي أساسًا يمكن اختباره بلا لمس مسار البيع.

## 6. المخاطر

- **الإنتاج:** الموقع الحي منشور (`alawalpro.online`). نلتزم بترحيلات إضافية فقط، ولا نغيّر جداولًا قائمة، ونكتب خطة تراجع لكل مرحلة في [قائمة النشر](../ui-redesign/deploy-checklist.md).
- **الأداء:** `Sale::save_value` سيصبح أثقل بعدة إدخالات. نقيس زمن حفظ البيع قبل وبعد.
- **الابتعاد عن المصدر الأصلي:** الفرع بعيد أصلًا عن OSPOS الأصلي. نحصر كل كود المحاسبة في مجالات أسماء معزولة، وندخل على الملفات الحالية بخطافات صغيرة فقط.
- **التقريب:** يجب أن يتبع الترحيل نمط التقريب الحالي (`Rounding_mode`) حتى لا يختلف إجمالي القيد عن إجمالي الفاتورة بفلس.
- **حقوق المنتج:** نستلهم الوظائف ولا ننسخ شيفرة دفترة ولا نصوصها ولا هويتها ولا ترميز حساباتها.
