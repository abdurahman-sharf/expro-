# التصميم المعماري للطبقة المحاسبية

> **الحالة:** تصميم مقترح للمراجعة، لم يُكتب منه كود. البنود المعلَّمة **[تحقق]** تحتاج فحصًا في الشيفرة أو قرارًا منك قبل التنفيذ (انظر [04](04-roadmap.md)).

## 1. المبادئ

1. **دفتر أستاذ واحد هو مصدر الحقيقة المحاسبية.** كل تقرير مالي يُقرأ منه وحده، لا من جداول العمليات.
2. **العمليات تبقى كما هي** وتُرحِّل إلى الدفتر. لا نعيد كتابة البيع ولا الاستلام.
3. **الترحيل في المعاملة نفسها** (`transStart` الموجودة): يفشل المستند كله أو ينجح كله.
4. **لا حذف ولا تعديل لقيد مُرحَّل.** التصحيح = قيد عكسي + قيد جديد، والأثر ظاهر في السجل.
5. **اختياري ومُغلق افتراضيًا** (`accounting_enabled`): عند الإطفاء لا قوائم ولا ترحيل ولا أي تغيير في السلوك الحالي، فلا يتأثر المستخدمون الحاليون.
6. **لا مبلغ سالب في سطر.** المبلغ السالب في العملية (مرتجع) يقلب الجانب (مدين↔دائن).

## 2. نموذج البيانات

بادئة `ospos_`، محرك InnoDB، `utf8mb4`، ترحيلات بنمط المشروع (صف في `app/Database/Migrations/` يستدعي سكربت SQL عبر `executeScript`) أو `Forge` حيث يلزم تحقق من القيود.

```sql
CREATE TABLE ospos_accounts (
  account_id    INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  parent_id     INT UNSIGNED NULL,
  code          VARCHAR(20)  NOT NULL UNIQUE,
  name          VARCHAR(255) NOT NULL,
  type          ENUM('asset','liability','equity','revenue','expense') NOT NULL,
  normal_side   ENUM('debit','credit') NOT NULL,
  is_group      TINYINT(1) NOT NULL DEFAULT 0,      -- مجموعة: لا يُرحَّل إليها مباشرة
  system_key    VARCHAR(50) NULL UNIQUE,            -- مفتاح التوجيه إن كان حسابًا نظاميًا
  status        ENUM('active','suspended','hidden') NOT NULL DEFAULT 'active',
  FOREIGN KEY (parent_id) REFERENCES ospos_accounts(account_id)
);

CREATE TABLE ospos_journals (
  journal_id        INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  number            VARCHAR(40)  NOT NULL,
  journal_date      DATE         NOT NULL,
  description       VARCHAR(255) NULL,
  source_type       VARCHAR(30)  NOT NULL,          -- manual, sale, receiving, expense, ...
  source_id         INT UNSIGNED NULL,
  status            ENUM('draft','posted') NOT NULL DEFAULT 'posted',
  reverses_id       INT UNSIGNED NULL,              -- القيد العكسي يشير لأصله
  active_source_key VARCHAR(60)  NULL,              -- 'sale:123' للقيد الحالي فقط، NULL لما عُكس
  created_by        INT NOT NULL,
  created_at        TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_active_source (active_source_key),  -- يضمن قيدًا واحدًا فعّالًا لكل مستند
  KEY idx_date (journal_date),
  KEY idx_source (source_type, source_id)
);

CREATE TABLE ospos_journal_lines (
  line_id      BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  journal_id   INT UNSIGNED NOT NULL,
  account_id   INT UNSIGNED NOT NULL,
  debit        DECIMAL(18,4) NOT NULL DEFAULT 0,
  credit       DECIMAL(18,4) NOT NULL DEFAULT 0,
  description  VARCHAR(255) NULL,
  partner_type ENUM('customer','supplier','employee') NULL,   -- دفتر مساعد للذمم
  partner_id   INT UNSIGNED NULL,
  CHECK (debit >= 0 AND credit >= 0 AND (debit = 0 OR credit = 0)),
  KEY idx_account (account_id, journal_id),
  KEY idx_partner (partner_type, partner_id),
  FOREIGN KEY (journal_id) REFERENCES ospos_journals(journal_id),
  FOREIGN KEY (account_id) REFERENCES ospos_accounts(account_id)
);
```

> `docs/INSTALL.md` يعلن دعم MySQL 5.7، وهو يقبل `CHECK` ولا يفرضه (يفرضه MySQL 8.0.16+ وMariaDB 10.2+). لذلك التحقق الحقيقي **في `Ledger_lib`** والقيد في القاعدة حزام أمان إضافي. أما `active_source_key` فيعمل على كل الإصدارات لأن `UNIQUE` يسمح بتعدد `NULL`.

جداول مساندة:

| الجدول | الغرض |
|---|---|
| `fiscal_years` | اسم، بداية، نهاية، حالة (مفتوحة/مقفلة) |
| `closed_periods` | نطاق تاريخ ومفتاح نشط؛ يرفض الترحيل والعكس داخله |
| `account_routes` | (`route_key` ⟶ `account_id`): حسابات التوجيه الآلي، وتتضمن مفاتيح مثل `sales_revenue`, `sales_returns`, `cogs`, `inventory`, `ar_control`, `ap_control`, `vat_output`, `vat_input`, `rounding`, `cash_over_short` |
| `payment_methods` | مفتاح ثابت (`cash`, `debit`, `credit`, `check`, `bank_transfer`, `wallet`, `due`, `giftcard`, `rewards`) ⟶ حساب. **يحلّ مشكلة النص المترجم** ([02 §4](02-ospos-audit.md)) |
| `sequences` | عدّاد لكل نوع مستند مع بادئة وعدد خانات؛ تسلسل مستقل للقيود اليدوية |
| `journal_log` | من عدّل ماذا ومتى (سجل التعديلات) |
| `cost_centers` + عمود `cost_center_id` في السطور | مرحلة لاحقة |
| `treasuries`, `fixed_assets`, `asset_depreciation` | مراحل لاحقة |

**لماذا `DECIMAL(18,4)`:** عملات 3 خانات (دينار كويتي/بحريني/ريال عماني)، وتتّسع للتقريب الوسيط. القيم المرحّلة تُقرَّب إلى خانات العملة عند التوليد.

## 3. الخدمة المحاسبية

`app/Libraries/Ledger_lib.php` (نمط المكتبات الحالي)، واجهتها:

```php
post(JournalDraft $draft): int            // يتحقق: توازن، فترة مفتوحة، حسابات غير مجموعات، ≥ سطرين
reverse(int $journalId, ?string $reason): int
repost(string $sourceType, int $sourceId, JournalDraft $new): int   // عكس الحالي + ترحيل الجديد ذريًا
```

- التوازن بـ`bcmath` (موجودة أصلًا كمتطلب)، لا بأعداد عشرية عائمة.
- فروق التقريب ضمن حد (مثلًا أقل من 0.05 بالعملة) تُرحَّل إلى `rounding`؛ فوق الحد يُرفض المستند برسالة واضحة بدل رمي استثناء صامت.
- كل مستند يملك **مُحوِّلًا** (`SaleJournalBuilder`, `ReceivingJournalBuilder`, `ExpenseJournalBuilder`…) يحوّل الصفوف المحفوظة إلى `JournalDraft`. فصل البناء عن الترحيل يجعل القواعد قابلة للاختبار دون قاعدة بيانات.
- **نقطة الاستدعاء:** داخل `Sale::save_value` و`Sale::update` و`Sale::delete` و`Receiving::save_value`/`delete_value` وما يماثلها، قبل `transComplete()` ([02 §4-9](02-ospos-audit.md)).

## 4. قواعد الترحيل

### 4.1 البيع (مكتمل، نقطة بيع أو فاتورة)

| الجانب | الحساب | المبلغ |
|---|---|---|
| مدين | حساب طريقة الدفع (`payment_methods`) لكل دفعة | `payment_amount − cash_refund` |
| مدين | `ar_control` (مع `partner = customer`) لدفعة «آجل» | المبلغ الآجل |
| مدين | بطاقات الهدايا / نقاط الولاء للدفع بها | قيمة الدفعة |
| دائن | `sales_revenue` | مجموع صافي البنود بعد الخصم وقبل الضريبة |
| دائن | `vat_output` (حساب لكل ضريبة) | `sales_items_taxes.item_tax_amount` |
| مدين/دائن | `rounding` | فرق التقريب النقدي وفروق الضريبة |
| مدين | `cogs` | Σ كمية × `item_cost_price` للأصناف `HAS_STOCK` |
| دائن | `inventory` | نفس المبلغ |

- **التكلفة لا تُرحَّل** إلا حيث يحدث تحريك مخزون فعلي: `stock_type = HAS_STOCK` و`sale_status = COMPLETED` (نفس شرط `Sale.php:645`).
- **المرتجع** (`SALE_TYPE_RETURN`): المبالغ سالبة فتنقلب الجوانب؛ الإيراد المقابل `sales_returns` (حساب مقابل للمبيعات)، والتكلفة تُعكس إلى المخزون.
- **عرض السعر، أمر العمل، المعلّق:** لا قيد. عربون أمر العمل (`cash_deposit`/`credit_deposit`) يُعالج في المرحلة C كدفعة مقدمة من عميل (التزام).
- **الإلغاء:** `reverse()` للقيد الفعّال. **تعديل الدفعات:** `repost()`.
- **[تحقق] الضريبة المتضمنة:** عند `tax_included` يكون سعر البند شاملًا للضريبة فيُستخرج الإيراد بالطرح لا بالجمع. تُثبَّت المعادلة باختبار يقارن مجموع القيد بمجموع `Sale_lib` لعدة سيناريوهات (متضمنة/غير متضمنة، خصم نسبة/مبلغ، ضريبتان متتاليتان) قبل أي ترحيل.

### 4.2 الاستلام (مشتريات)

| الجانب | الحساب | المبلغ |
|---|---|---|
| مدين | `inventory` | Σ (`item_unit_price` × الكمية × `receiving_quantity`) بعد الخصم |
| دائن | حساب طريقة الدفع | عند الدفع الفوري |
| دائن | `ap_control` (مع `partner = supplier`) | عند «آجل» |

- يُستعمل `item_unit_price` لا `item_cost_price` (الأخير هو التكلفة القديمة، `Receiving.php:147`).
- مرتجع المشتريات: كمية سالبة → تنقلب الجوانب.
- **[قرار] ضريبة المدخلات:** الاستلام لا يحفظ ضريبة. إما إضافة حقل ضريبة إلى الاستلام (مرحلة B) أو أن تُسجَّل ضريبة المدخلات عبر **المصروفات** والقيود اليدوية فقط.

### 4.3 المصروف

مدين حساب المصروف (يُربط بالتصنيف: عمود `account_id` جديد في `expense_categories`) بقيمة `amount − tax_amount`؛ مدين `vat_input` بقيمة `tax_amount`؛ دائن حساب طريقة الدفع. تفعيل «إلزام اختيار حساب المصروف» كما في المرجع.

### 4.4 ما بعد المرحلة B

| الحدث | القيد | يحتاج |
|---|---|---|
| تحصيل من عميل آجل | مدين خزينة / دائن `ar_control` | شاشة سند قبض |
| دفع لمورد | مدين `ap_control` / دائن خزينة | جدول دفعات للاستلام |
| فرق الصندوق عند الإقفال | مدين/دائن `cash_over_short` مقابل الصندوق | ربط `Cashup` |
| إصدار بطاقة هدية بقيمة | مدين نقدية / دائن التزام بطاقات الهدايا | اختيار الخزينة عند الإصدار (الإصدار اليوم لا يسجّل دفعة) |
| تسوية المخزون اليدوية | مدين/دائن «فروق جرد» / `inventory` | ربط `Inventory` |

> **تنبيه مخزون:** حساب `inventory` في الدفتر (مشتريات بسعرها الفعلي − تكلفة المبيعات) قد يختلف عن Σ كمية × `cost_price` الحالي لأن تكلفة الصنف قد تُحدَّث بالمتوسط. يلزم تقرير مطابقة بين الاثنين، وتسوية صريحة بدل إخفاء الفرق.

## 6. الفترات والإقفال

- أي ترحيل أو عكس بتاريخ داخل **فترة مغلقة** يُرفض، ويظهر سبب الرفض للمستخدم (إلغاء بيع قديم مثلًا). لا ترحيل صامت إلى تاريخ آخر.
- الإقفال السنوي: قيد يصفّر الإيرادات والمصروفات إلى `32 أرباح مرحّلة`، ويُنفَّذ بأمر صريح لا تلقائيًا.

## 7. التقارير (من الدفتر فقط)

| التقرير | مصدره |
|---|---|
| دفتر الأستاذ / كشف حساب | `journal_lines` لحساب ومدة، برصيد جارٍ |
| ميزان المراجعة (مجاميع وأرصدة) | تجميع السطور حتى تاريخ |
| قائمة الدخل | حسابات النوعين 4 و5 |
| الميزانية العمومية | الأنواع 1 و2 و3 + صافي الربح الجاري |
| التدفقات النقدية | حركة حسابات النقدية والبنك مصنّفة بمصدر القيد |
| إقرار ضريبة القيمة المضافة | `vat_output − vat_input` لمدة |
| كشف حساب عميل/مورد وأعمار الذمم | سطور الحسابات الرقابية حسب `partner_id` |

تُبنى بنمط تقارير `app/Models/Reports/` الحالي وتظهر في فهرس التقارير الموحد (P6) تحت مجموعة «المحاسبة»، وتُصدَّر PDF بقوالب P4 (mPDF/RTL).

## 8. الصلاحيات والقوائم

وحدات جديدة (صف `modules` + `permissions` + `grants` + مفاتيح لغة في كل `app/Language/*` بترتيب أبجدي، وإدخال في `NAVIGATION_GROUPS`/`NAVIGATION_ICONS`):

| module_id | الغرض |
|---|---|
| `accounts` | دليل الحسابات |
| `journals` | القيود اليومية |
| `accounting` | الإعدادات: التوجيه، طرق الدفع، الفترات، الأرصدة الافتتاحية |

التقارير المالية صلاحيات داخل وحدة `reports` كما تفعل `reports_expenses_categories` اليوم.

## 9. التفعيل والبيانات التاريخية

مُعالِج تفعيل من أربع خطوات: (1) اختيار قالب الدليل، (2) مراجعة التوجيه وطرق الدفع، (3) **تاريخ البدء** وأرصدة افتتاحية (قيد افتتاحي)، (4) اختياري: ترحيل رجعي للمبيعات والمشتريات والمصروفات السابقة بأمر `php spark ledger:backfill` يعمل على دفعات ويمكن إعادة تشغيله بأمان (تفرده من `active_source_key`).

التوصية: **ابدأ من أرصدة افتتاحية** وفعّل الترحيل الرجعي فقط إن لزم تقارير لفترات سابقة، لأن ترحيل تاريخ قديم يحمل أخطاء الإعدادات القديمة (نوع دفع بلغة أخرى، ضريبة متضمنة سابقة…).

## 10. الاختبار

اختبارات PHPUnit بملف لكل صنف وفق `AGENTS.md`، وأهم **الثوابت** (invariants) التي تُختبر:

1. مجموع المدين = مجموع الدائن في كل قيد، ولو بعد التقريب.
2. بيع ثم إلغاء → صافي الأثر صفر على كل حساب.
3. إعادة الترحيل لنفس المستند مرتين → قيد فعّال واحد فقط.
4. الترحيل داخل فترة مغلقة يُرفض ولا يترك بيعًا نصف محفوظ.
5. تبديل لغة النظام لا يغيّر حساب طريقة الدفع المستخرج من بيع قديم.
6. مطابقة: إيراد الدفتر + ضريبته = مجموع المبيعات في تقارير العمليات لنفس المدة.

وأمر `php spark ledger:verify` يفحص التوازن والتطابق على بيانات حقيقية بعد كل نشر.

## 11. بدائل نُظر فيها

| البديل | سبب الرفض |
|---|---|
| ربط OSPOS بنظام خارجي (Daftra عبر API، أو Odoo/ERPNext) | يحوّل النظام إلى واجهة لنظام آخر؛ المطلوب نظام محاسبي *متكامل داخله* |
| بناء التقارير المالية كاستعلامات فوق جداول العمليات بلا دفتر | لا يدعم القيود اليدوية ولا الفترات ولا مراكز التكلفة ولا ميزان المراجعة |
| ترحيل عبر أحداث `Model` | النماذج تستعمل `db->table()` لا أحداث النموذج ([02 §4-9](02-ospos-audit.md)) |
| ترحيل غير متزامن (طابور) | يسمح ببيع بلا قيد عند الفشل؛ نريد الذرّية |
