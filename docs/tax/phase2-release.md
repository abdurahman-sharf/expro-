# TAX2 — دليل تشغيل المرحلة الثانية (T14): Sandbox ثم Simulation ثم Production

| البند | القيمة |
|---|---|
| التاريخ | 2026-11-21 |
| **الحالة** | **دليل فقط، لم يُنفذ منه شيء.** لا اتصال بأي بيئة للهيئة، ولا OTP، ولا بيانات اعتماد |
| الموافقات | ثلاث موافقات مستقلة من المالك، كل منها قبل خطوتها: **D-10** (Sandbox)، و**D-20** (Simulation ببيانات المنشأة)، و**D-21** (Production) |

## 1. ما بُني ليُستعمل في هذه المرحلة (T9 إلى T12)

| القطعة | الدور |
|---|---|
| `einvoice_units` و`einvoice_unit_counters` | وحدة لكل شركة، تتسلم عداد الشركة بالرقم نفسه والـ hash نفسه (لا كسر للسلسلة) |
| `CsrBuilder` | طلب الشهادة على الخادم بمفتاح secp256k1 جديد لا يغادره، بحقول الهيئة وقالب البيئة (`TSTZATCA` / `PREZATCA` / `ZATCA`) |
| `OnboardingService` | شهادة الامتثال بـ OTP بوابة فاتورة، ثم شهادة الإنتاج. لصاحب `acc_einvoicing_onboard` وحده (لا تمنحها الأدوار) |
| `KeyVault` و`EInvoiceCredentials` | الأسرار والمفاتيح مختومة بمفتاح رئيسي في ملف خارج التطبيق والقاعدة و`.env`، بصلاحية 0600، وتدوير بـ `einvoice:rotate_key` |
| `einvoice_outbox` و`SubmissionService` | طابور بإيجار ورمز حماية: لا مستند يُرسل مرتين بنجاح، والمرفوض نهائي، وعطل الخدمة يُعاد لاحقًا، وانعدام الرد يُعاد بالطلب نفسه حرفيًا |
| `einvoice_submissions` و`einvoice_cleared_documents` | سجل إلحاقي لكل محاولة وردها، والـ XML المعتمد للقياسية |
| `ZatcaClient` و`ZatcaOnboardingClient` | واجهتان. **لا تطبيق حقيقي لهما في Expro**، والتطبيق الوحيد وهمي للاختبارات. لا عنوان للهيئة في الكود |

## 2. ما يلزم بناؤه بعد الموافقة D-10 (لا قبلها)

1. عميل HTTP حقيقي يطبق الواجهتين، تُقرأ عناوين البيئات فيه من إعدادات لا من الكود، ويُختبر أولًا على Sandbox وحده.
2. شاشة «الربط مع ZATCA» لصاحب `acc_einvoicing_onboard`، وشاشة متابعة المستندات (المرسلة والمعلقة والمرفوضة) وإعادة المحاولة اليدوية.
3. تشغيل `einvoice:dispatch` بالعميل الحقيقي من cron كل دقيقة.
4. إعادة إصدار الفاتورة القياسية المرفوضة بمصدر مستقل (D-24 أ).
5. تنبيهات انتهاء الشهادات (30 و7 أيام) عبر `NotificationsEvaluate`.

## 3. الخطوات بعد كل موافقة

### 3.1 Sandbox (D-10)

1. حساب في بوابة المطورين باسم المالك (لا ينشئه المنفذ).
2. ملف المفتاح الرئيسي خارج التطبيق: `install -m 600 /dev/null /etc/expro/einvoice.key` ثم إضافة سطر مفتاح أول (`KeyVault::newKeyLine`)، ونسخه الاحتياطي **منفصلًا** عن نسخة القاعدة.
3. تسجيل الوحدة في Sandbox بالـ OTP التجريبي الموثق، وتشغيل فحوص الامتثال لكل نوع مستند، ثم شهادة الإنتاج من Sandbox.
4. إرسال كل عينات §5.3 عبر الطابور، وحفظ الطلبات والردود (بلا أسرار) للمراجعة.

### 3.2 Simulation (D-20)

بيانات المنشأة الحقيقية وOTP من بوابة فاتورة للمنشأة، ووحدة مستقلة بسلسلة مستقلة (لا تمس سلسلة الإنتاج). تشغيل تجريبي بكل الأنواع.

### 3.3 Production (D-21)

شهادة الإنتاج، ثم `einvoice_phase_two = 1`، ثم تشغيل محدود (فرع أو جهاز)، ثم التوسيع بقرار. **المستندات المرسلة لا تُسحب**، والتراجع بإيقاف الوحدة (`suspended`) والعودة إلى المرحلة الأولى للمستندات الجديدة إن سمح النظام.

## 4. قواعد لا تُكسر

- لا تمر بيانات اعتماد بالمحادثات ولا بالمستودع ولا بالسجلات.
- لا إعدادات إنتاجية قبل D-21.
- كل تغيير كود في هذه المرحلة على فرع ومراجعة، لا على الخادم مباشرة.
